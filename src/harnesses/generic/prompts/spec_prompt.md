## Spec Mode: `{{SPEC_MODE}}`

### Mode: bootstrap
Fresh start - generate all spec files from the user prompt.
- Create CONSTITUTION, WHY_WHAT, HOW from scratch
- Generate initial task list starting from ID 1

### Mode: adopt
Reverse-engineer AI docs from existing code (no AI artifacts exist).
- Read existing code in `{{CODE_DIR}}` to understand current architecture
- Generate CONSTITUTION that captures existing principles
- Generate WHY_WHAT documenting current features
- Generate HOW reflecting current architecture and patterns
- Create tasks for any NEW work the prompt requests (or empty if just documenting)

### Mode: extend
Add features to existing project (AI docs exist, minor enhancement).
- Preserve existing CONSTITUTION (immutable principles)
- Append to WHY_WHAT with new user stories
- Append to HOW only if new patterns are introduced (prefer no changes)
- Add new tasks with integer IDs continuing from highest existing ID
- Do NOT recreate or modify completed tasks

### Mode: extend-deep
Major feature addition (AI docs exist, significant changes).
- Same as extend, BUT may regenerate HOW.md if architectural changes needed
- Include BUILD_HISTORY.md context for pattern reuse
- Full context compression is available

### Mode: refresh-spec (legacy, backward compatibility)
Same as extend mode - reconcile existing project with new requirements.

## Task Breakdown Rules

1. **Substantial tasks** - Each task is a meaningful unit of AI Claude sonnet work (7-15 min), NOT micro-tasks
2. **Avoid over-granularity** - Group related changes into single tasks (e.g., "Add feature X with styling and event handler" NOT separate tasks for HTML, CSS, JS)
3. **Ordered** - Foundation first, features second, polish last
4. **Testable criteria** - Every task has clear pass/fail criteria
5. **Dependencies** - List task IDs this task depends on

**IMPORTANT: Prefer fewer, larger tasks over many small ones.** Make sure we assess how much a single claude sonnet can build in one session, not too small or too big in complexity

## CRITICAL: Task ID Numbering

- **New tasks use integer IDs only**: If existing tasks are 1-17, new tasks must be 18, 19, 20, etc.
- **NEVER use decimal IDs** (like 18.1, 18.2) for planned tasks, these are reserved for bugs and in execution assessments
- **Decimal IDs are RESERVED** for subtasks created automatically when validation fails
- When refreshing specs for an existing project, continue from the highest existing task ID + 1

## Current vs Future
- Use `{{CURRENT_STATE_SUMMARY}}` to capture what exists today (architecture, features, constraints).
- Use `{{FUTURE_PROMPT}}` to describe what must change/add.
- Include a **Delta Plan** that maps future requirements to tasks; preserve existing task IDs/status where possible.
