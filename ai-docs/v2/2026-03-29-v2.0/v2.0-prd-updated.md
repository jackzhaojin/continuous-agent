## TLDR

V2.0 is a four-part reboot of the agent ecosystem:

1. **Skills + Playbooks** — Split the knowledge library into technical primitives (`skills/`) and functional workflows (`playbooks/`). Skills are atoms (Playwright, Git, Gmail API). Playbooks compose skills to accomplish goals (build-from-plan, triage-deployment, eds-site-builder).

2. **Worker Execution Patterns** — Collapse the harness/worker binary into a single unified worker with a configurable `execution_pattern`. Four patterns replace two modes: `plan-then-execute`, `loop-until-progress`, `plan-mode`, and `deterministic-pipeline` (what was "harness mode").

3. **Agent Identity** — The executive agent gets a real email address (Gmail), a Notion guest presence, and a Slack account. It checks its inbox as part of the executive loop. You interact with it via email or Slack, not just markdown files.

4. **Executive Dashboard** — A Next.js/React app that renders a live ops view of the agent: goal pipeline, active worker status, needs-you queue, activity feed, skill health. Pure display layer — reads agent-written output files, no agentic logic of its own. Designed for local-to-cloud portability.

**One worker model. Two knowledge libraries. A real identity. A window into everything.**

## 1. Vision & Motivation

### The Problem (Unchanged from Original V2.0)

Three execution contexts exist today, each with their own way of storing "how to do things":

| Context | Where Knowledge Lives | Format |
|---------|----------------------|--------|
| Manual chat sessions | Jack's head + scattered prompt logs | Unstructured conversation |
| Harnesses (EDS, Generic) | Hardcoded markdown prompts in `src/prompts/` | Per-harness templates |
| Continuous Agent | `src/agentic/prompts/` + capability YAML | Versioned templates + confidence scores |

### The New Problems (Addressed in This Revision)

**Problem 4:** The original V2.0 draft mixed technical primitives (Playwright, Git) with functional workflows (build-from-plan, create-demo-video) into a single `skills/` library. A skill that says "use Playwright" is fundamentally different from a skill that says "build an EDS site." Conflating them makes both harder to maintain and reuse.

**Problem 5:** Two execution modes (harness, worker) is a false binary. The real axis is *how structured is the work* — from fully deterministic pipelines to open-ended exploration loops. A unified worker with a configurable execution pattern is more honest and more flexible.

**Problem 6:** The agent has no identity. It exists only as a process on a laptop. Interaction requires the human to go to a markdown file. The agent can't reach out. It can't participate in shared spaces. It feels like a tool, not a collaborator.

### The Solution

- **Split the library:** `skills/` = technical primitives. `playbooks/` = functional workflows that compose skills.
- **Unify execution:** One worker model with four execution patterns, replacing the harness/worker binary.
- **Give the agent an identity:** Gmail address, Notion guest presence, Slack account. Async interaction via real channels.

### Design Principles (Updated)

1. **Skills are atoms, playbooks are molecules** — Skills can't be further decomposed into reusable parts. Playbooks compose multiple skills to accomplish a goal.
2. **Agents have goals, skills have none** — A skill doesn't care why it's being used. An agent (via a playbook) decides to use Playwright for testing vs. for video creation.
3. **One worker, many patterns** — The worker is always the same infrastructure. The execution pattern changes how it behaves.
4. **Infrastructure is not a skill or playbook** — Loop mechanics, SDK integration, credential handling, state management stay as TypeScript code.
5. **Security boundaries stay in infrastructure** — Tool permissions, model selection, credential tiers — not in skills or playbooks.
6. **Everything improves from every execution** — Skills and playbooks both carry track records.
7. **The agent has a presence, not just a process** — Identity enables push communication, not just pull.

## 3. The Skills Library (Technical Primitives)

### What a Skill Is

A skill is a **technical primitive** — a self-contained description of how to use a tool, API, or system capability. Skills have no inherent goal. They don't care why they're being invoked. They describe the *how*, not the *what for*.

**A skill answers:** "How do I use Playwright?" not "How do I create a demo video?"
**A playbook answers:** "How do I create a demo video?" — and it reaches for the Playwright skill to do it.

### Skill Categories

```
skills/
├── playwright/             — Browser automation, testing, scraping, video capture
├── git/                    — Commit, branch, push, PR, merge, tag
├── bash/                   — Shell scripting, file ops, process management
├── filesystem/             — Read, write, move, glob, watch
├── http-client/            — REST calls, auth headers, response parsing
├── gmail-api/              — Read inbox, send, label, archive, thread management
├── notion-api/             — Pages, databases, blocks, comments, guests
├── slack-api/              — Messages, channels, DMs, reactions
├── elevenlabs-api/         — Voice synthesis, audio generation
├── github-cli/             — Issues, PRs, releases, forks via gh CLI
├── npm/                    — Install, build, publish, version
├── pm2/                    — Process management, logs, restart
├── ssh/                    — Remote command execution, file transfer
├── docker/                 — Build, run, push, compose
└── graph-api/              — Microsoft Graph (future, if M365 added later)
```

### What a Skill Is NOT

- Not a goal ("build an EDS site")
- Not a workflow ("research then build then validate")
- Not domain knowledge ("EDS naming conventions") — that lives in `playbooks/domain/`
- Not an agent behavior ("how to prioritize work") — that lives in `playbooks/executive/`

### Skill Format

```markdown
---
name: playwright
version: 1.0.0
category: skill
description: |
  Browser automation using Playwright. Use for testing, scraping,
  video capture, or any task requiring a real browser.

use_cases:
  - End-to-end testing of web applications
  - Scraping dynamic content that requires JavaScript
  - Recording demo videos via screen capture
  - Exploring and mapping web application structure

tools_required:
  - Bash (to run playwright CLI)
  - Node.js (>=18)

setup:
  - npm install playwright (if not present)
  - npx playwright install (downloads browsers, one-time)

tags: [browser, automation, testing, scraping, video]

track_record:
  total_executions: 0
  successes: 0
  failures: 0
  last_executed: null
  confidence: 0
  maturity: Declared
---

## Core Usage

### Running Tests
```bash
npx playwright test
npx playwright test --headed          # visible browser
npx playwright test --project=chromium
```

### Scripted Automation
```javascript
const { chromium } = require('playwright');
const browser = await chromium.launch();
const page = await browser.newPage();
await page.goto('https://example.com');
```

## Known Failure Modes

- **crypto.subtle unavailable:** Playwright context requires HTTPS or `--ignore-https-errors`
- **Flaky timing:** Use `waitForSelector` over fixed `sleep` delays
- **Video capture requires headed mode:** `{ headless: false, recordVideo: { dir: './videos' } }`

## Notes

For video recording specifically, see `playbooks/worker/create-demo-video/` which
composes this skill with elevenlabs-api for narration.
```

## 4. The Playbooks Library (Functional Workflows)

### What a Playbook Is

A playbook is a **functional workflow** — it describes how to accomplish a goal by composing skills. Playbooks have context requirements, goals, and explicit references to the skills they use.

**A playbook answers:** "How do I create a demo video?" — by composing `playwright` (capture) + `elevenlabs-api` (narration) + `git` (commit the output).

### Playbook Categories

```
playbooks/
├── executive/              — How the executive agent operates
│   ├── work-prioritization/
│   ├── goal-decomposition/
│   ├── strategy-selection/
│   ├── retry-persistence/
│   └── needs-you-writing/
│
├── worker/                 — What workers build and do
│   ├── build-from-plan/
│   ├── create-demo-video/
│   ├── triage-deployment/
│   ├── research-codebase/
│   ├── spec-write-all/
│   ├── commit-and-tag/
│   └── validate-output/
│
├── domain/                 — Domain knowledge (EDS, Next.js, Oracle VM, etc.)
│   ├── eds-conventions/
│   ├── nextjs-patterns/
│   ├── pkce-auth-flow/
│   ├── oracle-vm-deployment/
│   └── keycloak-config/
│
└── pipelines/              — Multi-step deterministic workflows (formerly "recipes")
    ├── eds-site-builder/
    └── generic-app-builder/
```

### Key Distinction: domain/ vs skills/

`skills/` primitives are tool/API knowledge — *how to use Playwright*.
`playbooks/domain/` is domain-specific declarative knowledge — *what EDS naming conventions are*, *how Keycloak CORS behaves*, *what the Oracle VM disk layout looks like*. Domain playbooks don't execute steps — they're reference context that workers load when operating in a specific domain.

### Playbook Format

```markdown
---
name: create-demo-video
version: 1.0.0
category: worker
description: |
  Creates a narrated demo video of a web application.
  Composes Playwright for screen capture and ElevenLabs for AI narration.

execution_pattern: plan-then-execute   # Default for this playbook

composes_skills:
  - playwright                          # Screen capture
  - elevenlabs-api                      # AI narration
  - git                                 # Commit output

composes_playbooks:
  - domain/nextjs-patterns              # If app is Next.js

context_requires:
  - app_url: "URL of the running application"
  - script: "Narration script or high-level demo flow"
  - output_dir: "Where to save the final video"

context_optional:
  - voice_id: "ElevenLabs voice ID (defaults to standard)"
  - browser: "chromium, firefox, or webkit (default: chromium)"

tags: [video, demo, playwright, elevenlabs, presentation]

track_record:
  total_executions: 0
  successes: 0
  failures: 0
  last_executed: null
  confidence: 0
  maturity: Declared
---

## Overview

This playbook produces a narrated screen recording of a running web app.
The agent drives the browser via Playwright while ElevenLabs generates voiceover.

## Procedure

### Phase 1: Plan the demo flow
...

### Phase 2: Generate narration audio
...

### Phase 3: Capture screen recording
...

### Phase 4: Combine and commit
...

## Known Failure Modes

- ElevenLabs rate limits: back off 5s between audio generation calls
- Playwright video requires headless: false — ensure display is available
```

### Pipelines (Formerly Recipes)

Pipelines are playbooks with `execution_pattern: deterministic-pipeline`. They define a fixed ordered sequence of steps where each step's output feeds the next. What was previously the `recipes/` category and the harness mode is now `playbooks/pipelines/` with the `deterministic-pipeline` pattern.

```markdown
---
name: eds-site-builder
category: pipeline
execution_pattern: deterministic-pipeline

pipeline_steps:
  - step: 1
    name: spec-constitution
    playbook: worker/spec-write-all
    worker_type: research
    condition: bootstrap_or_adopt
    output: CONSTITUTION.md

  - step: 2
    name: research
    playbook: worker/research-codebase
    worker_type: research
    output: research.md

  - step: 3
    name: build
    playbook: worker/build-from-plan
    worker_type: build
    retries: 3
    output: code_changes

  - step: 4
    name: validate
    playbook: worker/validate-output
    worker_type: validate
    retries: 2
    output: validation_result
---
```

## 5. Worker Execution Patterns

### The Old Model vs The New Model

**Old model (binary):**
- Harness mode → deterministic recipe pipeline
- Worker mode → agentic, runs until done or max turns

**New model (four patterns, one worker):**
Everything is a worker. The `execution_pattern` field in PROMPT.md frontmatter (or in the playbook itself) determines how the worker behaves. The same spawner infrastructure handles all four patterns.

### The Four Patterns

#### Pattern 1: `plan-then-execute` (Default)

The worker first produces a plan, gets it reviewed/logged, then executes. Good for tasks where the scope is partially known and research should precede building.

```
Worker starts
  └── Phase A: Research and plan (read-only tools, no writes)
       └── Produces: plan.md with steps and approach
  └── Phase B: Execute plan (write tools enabled)
       └── Follows plan.md, adapts as needed
  └── Phase C: Validate and commit
```

**When to use:** Build tasks, spec tasks, any work where thinking first prevents wasted effort.

#### Pattern 2: `loop-until-progress`

The worker runs in a continuous loop, making incremental progress on each iteration. The loop continues as long as the verifier reports forward movement. Stops when stuck (no progress in N iterations) or when the DoD is met.

```
Worker starts
  └── Iteration 1: Attempt next chunk of work → verifier checks progress
  └── Iteration 2: Continue from where left off → verifier checks progress
  └── Iteration N: DoD met → done
       OR: N iterations with no progress → blocked, queue in needs-you.md
```

**When to use:** Long-running builds, exploratory work where the path isn't fully known, tasks that benefit from 24/7 momentum over burst effort.

#### Pattern 3: `plan-mode`

The worker produces a comprehensive plan and stops — it does NOT execute. The plan is written to a structured document, committed, and queued for human review or for a follow-on `plan-then-execute` worker. Mirrors Claude Code's plan mode.

```
Worker starts
  └── Deep research phase (no writes to output)
  └── Produces: comprehensive PLAN.md
       ├── Full approach with phases
       ├── File list and changes
       ├── Known risks and alternatives
       └── Estimated complexity
  └── Commits PLAN.md, writes to needs-you.md for review
  └── Stops — does not build
```

**When to use:** Complex or risky tasks where human review of the approach is valuable before any code is written. Architecture decisions, major refactors, multi-week work.

#### Pattern 4: `deterministic-pipeline`

A fixed ordered sequence of steps (what was previously "harness mode"). Each step spawns its own worker with a specific playbook. Step N's output is the input to step N+1. Used by `playbooks/pipelines/`.

```
Pipeline executor reads pipeline steps from playbook
  └── Step 1: Spawn worker (research type) with playbook A → output: doc A
  └── Step 2: Spawn worker (build type) with playbook B + doc A → output: code
  └── Step 3: Spawn worker (validate type) with playbook C + code → Pass/Fail
  └── On fail: create subtask, insert before next step, retry
```

**When to use:** Structured multi-agent workflows where the steps are known in advance. EDS site building, generic app building from a PRD.

### How execution_pattern Is Set

Priority order:
1. **PROMPT.md frontmatter** — human or agent sets `execution_pattern: plan-mode` explicitly
2. **Playbook default** — the playbook's own frontmatter declares its preferred pattern
3. **System default** — `plan-then-execute` if nothing else is set

```yaml
# PROMPT.md frontmatter example
---
title: Redesign authentication flow
execution_pattern: plan-mode    # Think before touching anything
priority: P1
---
```

### Phase 4 Routing (Updated)

```
Phase 3: Select work → returns goal PROMPT.md

Phase 4: Route by execution_pattern
  Read execution_pattern from PROMPT.md (or playbook default, or system default)

  plan-then-execute      → worker-spawner.ts with plan-execute mode flag
  loop-until-progress    → worker-spawner.ts with loop mode flag + progress verifier
  plan-mode              → worker-spawner.ts with plan-only flag (no write tools in Phase B)
  deterministic-pipeline → pipeline-executor.ts (reads pipeline steps from playbook)

Phase 5: Execute via appropriate executor

Phase 6: Validate (same regardless of pattern)
Phase 7: Update state (same regardless of pattern)
```

## 6. Agent Identity

### Vision

The executive agent gets a real identity: an email address, a presence in Notion, and a Slack account. This changes the interaction model from *pull* (you check needs-you.md) to *push* (agent emails/Slacks you when it needs something). The agent goes from being a process you visit to a collaborator that participates in your shared spaces.

### Email: Gmail API

**Setup (one-time, human does this):**
1. Create `exec.agent.{yourname}@gmail.com`
2. Create a Google Cloud project, enable Gmail API
3. Create OAuth2 credentials, run one-time auth flow, store refresh token in agent `.env`
4. From this point: fully API-driven, no 2FA prompts, no browser needed

**What the agent can do:**
- Read inbox (filter by sender, subject, label)
- Send email from its own address
- Label and archive processed emails
- Reply to threads

**What this enables:**
- You email the agent: "Reprioritize the dashboard goal to P1" → agent parses on next loop, updates PROMPT.md
- Agent emails you: "Blocked on authentication — need your decision on OAuth vs API key"
- Agent sends weekly summary email with what it accomplished
- Any tool or service can email the agent to trigger workflows

**New module:** `src/identity/gmail-client.ts`
**New skill:** `skills/gmail-api/SKILL.md`

### Executive Loop: Phase 0.5 — Check Inbox

A new phase added before Phase 1 (Health Check). Runs every N iterations (configurable, default: every iteration or every 5 minutes of wall time):

```
Phase 0.5: Check Inbox

1. Fetch unread emails to agent address via Gmail API
2. For each email:
   a. Parse intent (priority change, new goal, approval, question answer)
   b. If actionable: add to input queue (same as needs-you.md processing)
   c. If unclear: reply asking for clarification, archive
   d. Label as "processed" and archive
3. Continue to Phase 1
```

Email becomes a first-class input channel alongside needs-you.md. The agent doesn't distinguish between "Jack wrote in needs-you.md" and "Jack emailed the agent" — both are instructions processed the same way.

### Notion: Guest Presence

**Setup (one-time, human does this):**
1. Invite `exec.agent.{yourname}@gmail.com` to the Notion workspace as a guest
2. Grant access to relevant databases (Milestones, Goals, Daily Summaries)
3. Agent uses existing `NOTION_API_KEY` in `.env` for API access (already set up in V1.2)

**What changes:**
- Notion updates are now attributed to the agent as a real collaborator, not just anonymous API writes
- Agent can leave comments on Notion pages (visible as the agent's identity)
- Future: agent has its own Notion pages it maintains (status, capabilities, active goals)

**New skill:** `skills/notion-api/SKILL.md` (the API mechanics)
**Existing:** Notion reporting logic stays in `src/deterministic/notion-reporter.ts`

### Slack: Push Notifications

**Setup (one-time, human does this):**
1. Create Slack account for agent using agent Gmail address
2. Join workspace, create DM channel with you
3. Store Slack bot token in agent `.env`
4. Agent uses Slack API for sending (inbound Slack → agent is V3.0)

**What the agent can do in V2.0:**
- Send DMs to you when something needs attention
- Post to a designated `#agent-updates` channel
- Format messages with blocks (structured summaries, not just plain text)

**What this enables:**
- Agent pings you in Slack instead of (or in addition to) needs-you.md
- You get a Slack message: "🔴 Blocked on harness-eds update — need your input"
- Daily Slack summary of what was built

**New module:** `src/identity/slack-client.ts`
**New skill:** `skills/slack-api/SKILL.md`

### Identity Configuration

```bash
# .env additions for identity
AGENT_EMAIL=exec.agent.yourname@gmail.com
GMAIL_REFRESH_TOKEN=           # Set after one-time OAuth flow
GMAIL_CLIENT_ID=               # From Google Cloud project
GMAIL_CLIENT_SECRET=           # From Google Cloud project
SLACK_BOT_TOKEN=               # From Slack app settings
SLACK_CHANNEL_ID=              # Your DM channel or #agent-updates channel ID
IDENTITY_ENABLED=true          # Kill switch
```

### Constitution Compliance

Agent identity is **read-only by default** — the agent reads email and sends outbound messages. It cannot:
- Access your personal email (only its own address)
- Accept invitations or change account settings autonomously
- Post to public channels without approval (Constitution Section 3)
- Send bulk email or mass Slack messages

Outbound communication (email, Slack) is treated like writing to needs-you.md — it's the agent communicating status and requests, not publishing to the world.

## 7. Executive Dashboard

### Philosophy

The dashboard is a **pure display layer** — it has no agentic logic, makes no decisions, writes no files. It is a window into what the agent is already producing. The agent writes structured output; the dashboard renders it. This separation means the dashboard can be built, improved, or replaced entirely without touching the agent.

### Data Architecture: Agent Writes, Dashboard Reads

On every executive loop iteration (Phase 7), the agent writes a single pre-aggregated file:

```
workspace/dashboard-data.json
```

The Next.js dashboard reads this file via a Next.js API route (`/api/data`). The frontend never touches the filesystem directly — it always goes through the API route. This is the portability seam: when storage moves to the cloud, only the API route implementation changes. All React components stay identical.

```
Agent (executive loop Phase 7)
  └── Writes workspace/dashboard-data.json

Next.js API route (/api/data)
  └── Reads workspace/dashboard-data.json (today)
  └── Calls cloud store API (V3.0 — same route, same response shape)

React components
  └── Fetch from /api/data — never changes regardless of storage backend
```

### Worker Execution Trace (Turn-Level Visibility)

The activity feed captures milestone events (started, completed, blocked). That's not enough. The most important transparency gap is the **turn-by-turn tool call sequence** — what did the worker do each turn, why, what came back, and what did it decide to do next.

#### What Gets Logged Per Turn

Every worker turn is logged to a per-worker trace file:

```
ledgers/{date}/traces/worker-{task-id}-trace.jsonl
```

Each line is one turn:

```json
{
  "turn": 12,
  "timestamp": "2026-03-28T14:22:31Z",
  "thinking": "The build failed because npm install didn't run first. I need to check if node_modules exists before trying to build.",
  "tool_calls": [
    {
      "tool": "Bash",
      "input": "ls -la node_modules 2>/dev/null | head -5",
      "output": "ls: cannot access 'node_modules': No such file or directory",
      "duration_ms": 210
    },
    {
      "tool": "Bash",
      "input": "npm install",
      "output": "added 847 packages in 12s",
      "duration_ms": 12400
    }
  ],
  "turn_result": "progress",
  "next_intent": "Retry the build now that dependencies are installed"
}
```

**Fields:**
- `thinking` — the model's reasoning before tool calls (extracted from thinking blocks if available, otherwise inferred from response text)
- `tool_calls` — ordered sequence: tool name, exact input, truncated output (first 500 chars), duration
- `turn_result` — `progress` | `blocked` | `error` | `complete`
- `next_intent` — what the worker said it would do next (last sentence of response before next tool call)

#### How the Agent Writes This

The worker SDK already streams responses. The turn logger intercepts the stream and extracts tool use blocks. This happens in `worker-spawner.ts` where the stream is already being processed for ledger writes — it's an extension of existing logic, not a new tap.

```typescript
// src/agentic/execution/worker-spawner.ts (addition)
// For each SDK message event in the stream:
onTurn(turn) {
  const traceEntry = {
    turn: turn.index,
    timestamp: new Date().toISOString(),
    thinking: extractThinking(turn),
    tool_calls: turn.toolUseBlocks.map(t => ({
      tool: t.name,
      input: JSON.stringify(t.input),
      output: truncate(t.result, 500),
      duration_ms: t.durationMs
    })),
    turn_result: classifyTurnResult(turn),
    next_intent: extractNextIntent(turn)
  };
  appendToTrace(taskId, traceEntry);
}
```

The trace file is written incrementally — each turn appended immediately, so if the worker crashes you still have the trace up to that point.

## 8. Worker Agent Model

### Worker = Profile + Skills + Playbook

A worker agent is assembled from three parts:

**Worker Type Profile** (infrastructure — `worker-types/*.yaml`): defines security boundaries — tool permissions, model, max turns.

**Skills** (technical primitives — loaded from `skills/`): what tools the worker knows how to use. Playwright, Git, Gmail API, etc.

**Playbook** (functional workflow — loaded from `playbooks/`): what the worker is trying to accomplish and how. Composes skills with judgment.

The worker reads the playbook, understands the goal, and reaches for skills as needed. The playbook says "use Playwright for screen capture" — the worker reads the Playwright skill to know *how*.

### Worker Types (Unchanged in Name, Updated in Scope)

| Type | Permissions | Use Case |
|------|------------|----------|
| `research` | Read-only, web search | Codebase analysis, planning, research, plan-mode phase A |
| `build` | Read, write, bash, playwright (conditional) | Implementation, code generation |
| `validate` | Read-only, playwright (conditional) | QA, verification — cannot write = honest assessment |
| `self-enhance` | Read, write, bash (agent codebase only) | Agent self-modification on branches |
| `skill-build` | Read, write (skills/ and playbooks/ directories) | Skill/playbook creation and updates |
| `identity` | Read, write (email/Slack clients only) | Email responses, Slack notifications |

### Plan-Mode Worker Behavior

For `plan-mode` execution pattern, the `research` worker type is used but with a specific behavioral constraint: Phase B (execution) tool access is withheld. The worker produces `PLAN.md` and cannot write to the output project. This mirrors Claude Code's plan mode where the agent thinks comprehensively before touching anything.

## 10. Capabilities System

### Skill and Playbook Track Records

Both skills and playbooks carry their own `track_record` in frontmatter. The `skill-updater.ts` (replacing V1.x `capability-updater.ts`) writes to both after each execution:

```yaml
track_record:
  total_executions: 4
  successes: 3
  failures: 1
  last_executed: 2026-03-15
  confidence: 75           # 0-100
  maturity: Demonstrated   # Declared → Demonstrated → Reliable
```

**Confidence update rules (same as V1.x):**
- PASS: +10 (capped at 100)
- FAIL: -15
- 3+ consecutive failures: flag for human review

**Maturity progression:**
- Declared: exists, not yet tested
- Demonstrated: ≥1 PASS
- Reliable: ≥3 PASS, <20% failure rate

### Auto-Generated Summary

`capabilities/summary.yml` is auto-generated from all skill and playbook track records — a flat view of what the agent knows how to do at all confidence levels.

## 11. Skill & Playbook Lifecycle

### Improvement Pattern (Same for Both)

```
Execution completes (any pattern)
  └── Phase 7b: Did this reveal something new?
       ├── New failure mode not documented in the skill/playbook?
       ├── Successful workaround that contradicts current guidance?
       └── Better approach discovered?

  If yes → create [SKILL-UPDATE] or [PLAYBOOK-UPDATE] draft goal
         → skill-build worker creates branch: skill-update/{name}-{date}
         → human reviews and merges
         → immediately active on next loop iteration
```

### What the Agent Can and Cannot Do

| Action | Allowed |
|--------|---------|
| Read skills and playbooks | ✅ Always |
| Propose updates (via branch + needs-you.md) | ✅ Always |
| Silently modify skill/playbook content | ❌ Never |
| Create new skills from scratch (via skill-build worker) | ✅ With human review |
| Delete skills or playbooks | ❌ Never (archive only) |

## 16. Constitution Implications

### Section 3 (External Publishing)

Agent email and Slack are **intra-team communication**, not external publishing. The agent emails you (the owner) and posts to your private Slack workspace. This is equivalent to writing to needs-you.md — internal, private, to the owner. No Constitution amendment needed.

If the agent ever posts to a public channel or sends email to third parties, that requires explicit approval (same as any external publishing).

### Section 6 (Output Isolation)

Skills and playbooks live in `skills/` and `playbooks/` under the continuous-agent repo. They are **agent infrastructure** (like prompt templates), not worker output. No Constitution amendment needed.

### Section 7 (Mandatory Logging)

All skill and playbook executions logged to:
- `skills/{name}/history/executions.jsonl` or `playbooks/{name}/history/executions.jsonl`
- Existing `ledgers/work-ledger.jsonl`

## 18. Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Skills/playbooks boundary confusion** | Team (and agent) put functional workflows in skills/ | SKILL.md format validation: reject files with `context_requires` or `composes_playbooks` in skills/ (those belong in playbooks/) |
| **Gmail OAuth token expiry** | Phase 0.5 fails silently, inbox not checked | Refresh token has very long TTL; add explicit token health check in Phase 0.5 with needs-you.md alert on auth failure |
| **Email parsing misinterprets instructions** | Agent takes wrong action from ambiguous email | Conservative parser: if intent is unclear, reply asking for clarification rather than acting. Log all parsed intents. |
| **Prompt builder rewrite breaks workers** | Workers receive bad prompts | Feature-flag: keep old templates as fallback. Shadow mode: run both and compare outputs before cutover |
| **Pipeline executor diverges from harness** | EDS builder produces different output | Keep original harness runnable for comparison. Validate same input → same output |
| **Slack notification spam** | You get too many messages | Configurable throttle: max N Slack messages per hour. DM only for blocks and completions, not every step |
| **dashboard-data.json grows too large** | Dashboard slow to load as activity feed accumulates | Cap activity feed at last 200 events in the JSON. Full history stays in work-ledger.jsonl |
| **Dashboard out of sync with agent state** | Stale data shown if agent crashes mid-write | Agent writes to a temp file then atomically renames to dashboard-data.json — no partial reads |

## Appendix B: Format Specifications

### Skill SKILL.md Frontmatter (Minimal)

```yaml
---
name: playwright
version: 1.0.0
category: skill              # Always "skill" for skills/
description: |
  One-paragraph description of what this tool/API is and when to reach for it.

use_cases:
  - Bullet list of distinct use cases

tools_required:
  - Bash
  - Node.js (>=18)

tags: [browser, automation, testing]

track_record:
  total_executions: 0
  successes: 0
  failures: 0
  last_executed: null
  confidence: 0
  maturity: Declared
---
```

### Playbook SKILL.md Frontmatter (Richer)

```yaml
---
name: build-from-plan
version: 1.0.0
category: worker             # executive | worker | domain | pipeline
description: |
  One-paragraph description of what goal this accomplishes.

execution_pattern: plan-then-execute   # Default pattern for this playbook

composes_skills:
  - playwright               # Skills this playbook reaches for
  - git

composes_playbooks:
  - domain/nextjs-patterns   # Domain context loaded when project_type is nextjs

context_requires:
  - plan_document: "A structured plan with phases, file lists, acceptance criteria"
  - project_type: "nextjs | rust | python | eds | etc."
  - output_path: "Where to write project files"

context_optional:
  - existing_codebase: "Path to existing code if extending"

tags: [build, implementation, multi-phase]

track_record:
  total_executions: 0
  successes: 0
  failures: 0
  last_executed: null
  confidence: 0
  maturity: Declared
---
```
