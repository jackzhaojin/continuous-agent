# V2.1.4 Goal: Fix V2 Prompt Composition & Skill-Based Worker Instructions

**Status:** Planning (2026-04-05)

## Problem

V2 prompt composition is the active path (`V2_PROMPT_COMPOSITION=true`) but it's half-built. Critical worker instructions are either hardcoded in `prompt-builder.ts` TypeScript or sitting in dead V1 templates that nobody reads. The V2 system was designed to compose prompts from **skills and playbooks**, but in practice the skill loading is incomplete, so workers get thin prompts missing essential context.

**What's wrong today:**
- `buildV2ComposedPrompt()` builds prompts inline in TypeScript — monorepo rules, playwright testing, constitution limits are all hardcoded strings in `.ts` files
- `src/agentic/worker-prompts/` (V1 templates) is dead code — has good content nobody sees
- `ai-sandbox CLAUDE.md` template has instructions that only Claude reads (Kimi/Codex ignore it)
- Worker skills in `claude-files-to-output/skills/` are underutilized — mostly project-specific, not general worker instructions
- Per-vendor differences (tool names, capabilities) are not handled — same prompt goes to all vendors

## Core Architecture (MUST understand before implementing)

### Two-CWD Model

Workers and the executive run in different directories. This is how skills are separated:

```
EXECUTIVE (CWD = continuous-agent/)
├── .claude/skills/          ← Executive skills (work-selection, goal-breakdown, etc.)
├── .claude/agents/          ← Subagent definitions
├── .claude/rules/           ← Contextual rules
└── src/                     ← Agent infrastructure code

WORKER (CWD = ai-sandbox/)   ← ALL workers start here, regardless of vendor
├── .claude/skills/          ← Worker skills (synced from continuous-agent)
├── .claude/agents/          ← Worker agents (synced from continuous-agent)
├── CLAUDE.md                ← Generated by worker-spawner (Claude-only)
└── projects/                ← All project directories
```

### Skill Sync Pipeline (already exists)

`worker-spawner.ts` line 233-238 runs `cpSync()` before every worker spawn:

```
continuous-agent/claude-files-to-output/    ──cpSync──>    ai-sandbox/.claude/
├── skills/{name}/SKILL.md                                ├── skills/{name}/SKILL.md
└── agents/{name}.md                                      └── agents/{name}.md
```

**To add a new worker skill:** create it in `continuous-agent/claude-files-to-output/skills/{name}/SKILL.md`. It will be synced to `ai-sandbox/.claude/skills/` on next worker spawn.

### Vendor Behavior at ai-sandbox CWD

| Vendor | CWD | Reads `.claude/skills/`? | Reads `CLAUDE.md`? | How it gets instructions |
|--------|-----|--------------------------|---------------------|------------------------|
| **Claude** | `ai-sandbox/` | Yes (SDK auto-discovers) | Yes (SDK auto-loads) | V2 prompt + CLAUDE.md + Skills via Skill tool |
| **Kimi CLI** | `ai-sandbox/` | **NO** | **NO** | V2 prompt string ONLY — everything must be injected |
| **Codex** | `ai-sandbox/` | **NO** | **NO** | V2 prompt string ONLY |

**Critical implication:** For Kimi and Codex, the V2 prompt builder must **read worker skill SKILL.md files and inject their content** into the prompt string. Claude gets them for free via the SDK.

## Requirements

### R1: Convert All Worker Instructions to Skills in `claude-files-to-output/skills/`

Every piece of worker context should be a SKILL.md file, not a hardcoded string in `prompt-builder.ts`:

| Instruction | Currently Lives | Should Be |
|-------------|----------------|-----------|
| Monorepo rules ("work in your project dir") | Dead V1 template `worker-base-v2.1.0.md` | `claude-files-to-output/skills/worker-base/SKILL.md` |
| Constitution limits | Dead V1 template | `claude-files-to-output/skills/worker-base/SKILL.md` |
| Web project testing (playwright-cli) | Hardcoded in `prompt-builder.ts` | `claude-files-to-output/skills/web-testing/SKILL.md` |
| Navigation & assessment ("check existing code first") | Dead V1 template | `claude-files-to-output/skills/worker-base/SKILL.md` |
| Reference POC pointers | Dead V1 template | `claude-files-to-output/skills/worker-base/SKILL.md` |
| Technology preferences (JS > Python) | Dead V1 template | `claude-files-to-output/skills/worker-base/SKILL.md` |
| Execution pattern behaviors | Hardcoded in `prompt-builder.ts` | Per-pattern skills or in `worker-base` |

**After this work:** `buildV2ComposedPrompt()` should have near-zero hardcoded instruction text. It should:
1. Build the objective section (title, description, constraints, DoD)
2. Read relevant SKILL.md files from `ai-sandbox/.claude/skills/` (already synced there by the copy pipeline)
3. Select which skills to load based on task type (web project → `web-testing`), vendor, and playbook references
4. For Kimi/Codex: inject full skill content directly into prompt string (they can't read `.claude/skills/`)
5. For Claude: lighter injection — SDK auto-discovers skills, only inject critical context
6. Load matched playbook if any
7. Concatenate and return

**The skill loading flow:**
```
worker-spawner.ts: cpSync(claude-files-to-output/, ai-sandbox/.claude/)  ← sync skills
prompt-builder.ts: read SKILL.md files from ai-sandbox/.claude/skills/   ← load skills
prompt-builder.ts: inject skill content into prompt for Kimi/Codex       ← build prompt
worker-spawner.ts: spawn worker with CWD=ai-sandbox/                     ← run worker
```

### R2: Skill-Based Web Testing with Playwright

Create `claude-files-to-output/skills/web-testing/SKILL.md` that enforces `playwright-cli` usage for all web projects.

**The skill must include:**
- Pre-flight check: verify site loads BEFORE coding (don't build on broken foundation)
- Post-build verification: open browser, snapshot, screenshot, click interactive elements
- Full `playwright-cli` command reference with exact paths
- Explicit framing as hard requirement (Kimi ignores soft instructions — proven in this session)

**How it gets loaded:**
- V2 prompt builder detects web project (tags, title keywords) → reads `web-testing/SKILL.md` → injects into prompt
- For Claude workers: skill is also available via Skill tool at `ai-sandbox/.claude/skills/web-testing/`

### R3: Per-Vendor Prompt Adaptation

The V2 prompt builder needs to know which vendor it's building for and adapt accordingly:

- **Claude:** Lighter prompt — SDK auto-loads CLAUDE.md and skills. Only inject objective, constraints, DoD
- **Kimi CLI (--yolo):** Heavy prompt — must contain ALL instructions. Tool names: Shell (not Bash), ReadFile (not Read), WriteFile (not Write), StrReplaceFile (not Edit). Everything from CLAUDE.md and relevant skills must be inlined
- **Codex:** Similar to Kimi — prompt-only, own tool naming. Needs investigation

**Implementation options (decide during work):**
- **Option A:** Universal skills + vendor preamble skill (`skills/vendor-kimi/SKILL.md` with tool name mappings)
- **Option B:** Vendor adapter layer in prompt builder that translates after skill loading
- **Option C:** Vendor-specific skill variants (`web-testing-kimi.md`, `web-testing-claude.md`)

- Update CLAUDE.md to remove any references to `worker-prompts/`

### R5: Testable Prompt Output

Assertions per vendor:

### R6: Breakdown Auto-Insert Regression Steps

The breakdown system should automatically insert testing-only steps for web projects:
- Every 5-8 build steps, insert a "regression test: verify with playwright-cli" step
- These steps have no build work — purely visual verification
- Already proven to work (Kimi spent 55 turns doing thorough visual testing in this session)

## Lessons Learned (Session 2026-04-05)

1. **Wire protocol inflates turn counts** — Kimi wire counted 1105 "turns" for 100 actual steps. Switched default to CLI.
2. **V2 prompt path ignores worker-prompts/** — all V1 template edits had no effect. Always verify in worker logs.
3. **Kimi follows explicit instructions, ignores soft ones** — exact commands with full paths = followed. "Test your work" = ignored.
4. **CLAUDE.md is Claude-only** — Kimi/Codex don't read it. Everything must be in the prompt string for non-Claude vendors.
5. **Regression test steps work** — dedicated playwright-cli testing step produced thorough visual verification (55 turns, all components confirmed rendering).
6. **Skills are the right abstraction** — they're loaded dynamically, vendor-agnostic in format, and human-readable. Instructions should live in skills, not TypeScript.
7. **The copy pipeline exists** — `claude-files-to-output/` → `ai-sandbox/.claude/` is already wired up. Use it.
